# arknet

## Projekt

- **arknet** (Architecture + Knowledge Net) — DDD-Architekturmodelle, die Maschinen verstehen
- Status: Konsolidierung aus doc42 + dddprocess + ddd-forge
- Produktvision: `docs/produktvision.adoc`

## Architektur

- Pipes & Filters: Turtle → Parse → Validate (SHACL) → Triple Store (RDF4J) → SPARQL → Template → AsciiDoc → HTML/PDF
- Delivery: **MCP-first** + CLI als Convenience-Layer
- Editionen/Store: lokaler Single-User-Client, Store hinter domaennahem Out-Port austauschbar (kognio-rdf lokal = Community/OSS <-> kognio-memory remote = Closed). Siehe `docs/adr/adr-001-local-client-and-swappable-store.md` (Client+Store), `adr-002-open-core-editions.md` (Editionen), `adr-003-adapter-b-remote-store.md` (Adapter B), `adr-004-spring-ai-mcp-tech-line.md` (Spring-AI-Tech-Linie fuer MCP), `adr-005-store-first-model-lifecycle.md` (Store-first: der Store ist der primaere Modell-Ort; Datei-Pipeline / `arknet_*`-Tools aussterbend), `adr-006-generic-store-read-path.md` (generischer BC-uebergreifender Store-Lesepfad `store_overview`/`resource_get` im Composition Root), `adr-007-shared-shacl-write-gate-module.md` (geteiltes SHACL-Write-Gate als eigenes technisches Modul statt Shared Kernel; grenzt gegen ADR-006 ab), `adr-008-in-adapter-as-bc-gateway.md` (In-Adapter darf einen Nachbar-BC-In-Port konsumieren -- Tor zum BC, nicht Teil von dessen Core; die "kein BC am anderen"-Invariante bindet nur noch die `*-core`; grenzt gegen ADR-006 und ADR-007 ab)
- CLI: **nicht implementiert**. Produktvision haelt an einem CLI als CI/CD-Convenience-Layer fest -- ein store-first-Neuschnitt, wenn der CI-Bedarf konkret wird.
- Keine Datei-Pipeline: `arknet-core`, `arknet-projection` und die datei-basierten `arknet_*`-MCP-Tools existieren nicht mehr. Store-first (die BC-Tools) ist der einzige Modell-Lebenszyklus (ADR-005). Einziger generierender Ausgabepfad ist das self-contained `store-report.html`.

## Tech-Stack

- Java 25+ (`release 25`; io.kogn.rdf ist Java-25-gebaut), Maven Multi-Module
- Bauen/Testen: shell-`mvn` (default JDK 25); JDT-MCP kann `--release 25` (noch) nicht
- RDF4J 6.x (Triple Store + SHACL Sail)
- AsciidoctorJ + asciidoctor-diagram (AsciiDoc → HTML/PDF)
- PlantUML (Diagramme)
- Mustache (Templates fuer AsciiDoc-Generierung)
- Spring AI 2.0 (Tech-Linie fuer den MCP-Layer -- `@McpTool`)
- kognio-rdf (`io.kogn.rdf`, embeddable RDF-Substrat hinter Out-Ports; OSS github.com/kogn-io/rdf-core)
- Turtle (.ttl) als Primaerformat

## Maven-Module

- **arknet-ontology**: nur .ttl-Ressourcen (Ontologie-Module, Shapes)
- **arknet-mcp**: MCP-Server (stdio) + Composition Root -- Spring Boot/Spring AI 2.0, verdrahtet requirements-Hexagon + ubiquitous-language-Hexagon + use-cases-Hexagon als `@McpTool`-Beans. Die BC-Hexagons teilen den `WorkspaceId`-Bean UND einen gemeinsamen `DatasetLifecycle`-Bean -- ein Store pro Workspace. Beherbergt zusaetzlich den generischen, BC-uebergreifenden Store-Lesepfad (`store_overview`/`resource_get`, readOnly; ADR-006) -- Logik in `mcp/store/`, kein eigener BC.
- **arknet-shared-kernel**: DDD Shared Kernel -- technologieneutrale, von mehreren BCs geteilte Domain-Bausteine: `de.hauschel.arknet.kernel.WorkspaceId` sowie die opake Ressourcen-Identitaet `ResourceId` (sealed, `of(String)` wrapt eine bestehende `https://`-IRI und validiert im Konstruktor vollstaendig: `https://`-Prefix, keine Whitespace UND keine der IRIREF-verbotenen Zeichen `<>"{}|^\`\`+Steuerzeichen -- dieselbe Zeichenregel wie `SparqlTerms.isValidIriReference` in `arknet-persistence-support`, notwendig dupliziert, da der Kernel nicht am Support haengen darf), `ResourceIdFactory`-Port + `UuidResourceIdFactory` (mintet flach unter `https://w3id.org/arknet/id/<uuid>`, kein BC-/Typ-Segment -- der Typ lebt in `rdf:type`). Zusaetzlich `DisplayLocale` (Record `requested`/`systemDefault: Locale`, statische `DEFAULT`-Instanz, Methode `select(Collection<LocalizedLiteral>)`) und `LocalizedLiteral` (Record `value`/`languageTag`, technologieneutrale Projektion eines sprachgetaggten RDF-Literals) -- die Anzeige-Sprachauswahl fuer mehrsprachige `skos:prefLabel`-Literale, ueber eine vierstufige Fallback-Kette: angefordertes Locale -> System-Default -> ungetaggtes Literal -> deterministischer Fallback ueber eine stabile Sortierung (nie ein hartes `FILTER`, das eine Ressource ohne Label in der angeforderten Sprache stumm verschluckt). Liegt im Kernel aus demselben Grund wie `WorkspaceId`: ein Wert pro Prozess, einmal im Composition Root konfiguriert und in die Bounded Contexts injiziert. Bewusst winzig.
- **arknet-persistence-support**: technischer Support der kognio-rdf-Out-Adapter -- das von allen BCs geteilte SHACL-Write-Gate (`de.hauschel.arknet.persistence.ShaclWriteGate` + `WriteConstraintViolationException`, validate-before-commit). Zusaetzlich zwei technologieneutrale, RDF4J-freie Bausteine: `SparqlTerms` (SPARQL-Escaping inkl. LF/CR/TAB + IRIREF-Serialisierung `isValidIriReference`/`iriRef`) und `UnresolvedReferenceException` (didaktische Cross-BC-Ablehnung). Das Gate traegt zusaetzlich einen `enforce(candidate, assertedContext)`-Overload: validation-only Kontext-Tripel (synthetische Typen fuer Nachbar-Graph-Knoten) als **Parameter** -- weiterhin kein Kontextwissen im Gate (ADR-007). Bewusst KEIN Shared Kernel: der Kernel wird von den `*-core` konsumiert und muss dependency-frei bleiben, das Gate nur von den `*-adapter-kogniordf` -- ein Merge zoege die kognio-rdf-Ports in den Classpath der Cores. Die Trennung ist lasttragend, nicht Geschmack (hier wohnt zudem Technik, kein Domain-Vokabular). Trotz kognio-rdf-Abhaengigkeit RDF4J-frei -- das Gate kennt nur die `io.kogn.rdf.shacl`/`terms`-Ports, RDF4J bleibt in den Repository-Factories. Kontextunterschiede sind Konstruktor-Parameter (`shapes`/`axioms`/`options`), **kein Code im Gate**: req reasont ueber die Axiome (`subClassOf`, volle Shapes), ul uebergibt leere Axiome + `defaults()` (kein Reasoning), uc konstruiert Axiome/Options identisch zu req -- sein echter Unterschied sind **gefilterte** Shapes (`loadUseCaseShapes()` entfernt fremde `sh:targetClass`), und diese Filterung ist Code in der uc-Factory. Siehe ADR-007.
- **arknet-architecture-tests**: ArchUnit-Regeln fuer die Dependency-Invarianten, die der Modulschnitt NICHT erzwingen kann und die sonst lautlos erodieren. Nur `src/test`, kein Produktivcode, von niemandem konsumiert. Vier Regeln: `arknet-persistence-support` bleibt RDF4J-frei (die Eigenschaft, die ADR-007 traegt), nur die `KognioRdf*RepositoryFactory` nennt RDF4J-Typen (modulintern -- Maven kann das prinzipiell nicht sehen), die `*-core` bleiben frei von `rdf4j`/`io.kogn`, und dasselbe RDF4J/`io.kogn`-Verbot gilt fuer die `*-adapter-mcp` (gezielt nur `..adapter.mcp..`, nicht die pauschale `..adapter..`-Ausnahme von Regel 3, die sonst auch die In-Adapter faelschlich mit ausgeklammert haette; ADR-008s In-Adapter-zu-Nachbar-In-Port-Erlaubnis bleibt unberuehrt, da ein Nachbar-In-Port keine RDF-Technologie ist). Bewusst NICHT abgebildet: was der Modulschnitt schon haerter erzwingt (core haengt nicht am Adapter, kein `*-core` haengt an einem anderen BC) -- das waere Zeremonie. Die Invariante gilt fuer die `*-core`-Module, nicht pauschal fuer jedes Modul eines BC -- ein In-Adapter darf einen fremden In-Port konsumieren, er ist das Tor zum BC, nicht Teil von dessen Core (Beispiel: `arknet-requirements-adapter-mcp` -> `arknet-ubiquitous-language-core` fuer die read-only Anzeige-Aufloesung ResourceId -> TERM-N in `req_get`/`req_list`; `req_link_term`s Schreibpfad bleibt ueber `TermLookup` entkoppelt; ADR-008). Die Regeln lesen Bytecode, kein POM: eine ungenutzte `rdf4j-*`-Dependency bleibt unsichtbar (`maven-enforcer` waere das ergaenzende Werkzeug, bewusst out of scope).
- **arknet-requirements**: erste hexagonale BC -- arknet-requirements-core (Domaene/In-/Out-Ports) + arknet-requirements-adapter-kogniordf (Out) + arknet-requirements-adapter-mcp (In, Spring AI `@McpTool`). Requirement-Lifecycle. Ein Requirement traegt `arkreq:usesTerm`-Kanten auf Glossar-Begriffe (`req_link_term`): die Kante gehoert bewusst der requirements-BC (Domain `arkreq:Requirement`), damit die Abhaengigkeit requirements -> ubiquitous-language zeigt und nicht umgekehrt. Sie steckt **im** `Requirement`-Record, nicht daneben -- der Out-Adapter schreibt replace-by-identity, eine Kante ausserhalb des Aggregats wuerde der naechste `req_set_status` still loeschen. `TermRef` haelt die Subject-`ResourceId` des Ziels (keinen Business-Code); die Aufloesung Code -> Identitaet sitzt im `RequirementService` hinter einem eigenen Out-Port `TermLookup` (Impl `KognioRdfTermLookup`), didaktische Ablehnung bei Unbekanntem/Mehrdeutigem ueber `UnresolvedReferenceException`. Opake Identitaet statt schema-on-subjects: `RequirementId` wrapt eine vom Kernel gemintete `ResourceId` (Subject-IRI, unveraenderlich), `RequirementCode` traegt die `FR-N`/`NFR-N`-Semantik als reines Business-Label (`dcterms:identifier`) -- der MCP-Nutzer tippt weiterhin den Code, nie die IRI. `save` zerfaellt in `create` (Identitaet darf noch nicht existieren, sonst `ResourceAlreadyExistsException`) und `update` (Identitaet muss existieren, sonst `RequirementNotFoundException`); der Out-Adapter prueft das per `ASK` **innerhalb** der Schreibtransaktion (kein TOCTOU), `update` bleibt danach replace-by-identity. Seit #108 traegt der Out-Port zusaetzlich `compareAndUpdate` (liest den aktuellen Snapshot **innerhalb derselben** Schreibtransaktion und schreibt nur bei Uebereinstimmung mit dem beim Aufruf erwarteten Snapshot, sonst `false` statt eines stillen Overwrites) -- `RequirementService#setStatus`/`linkTerm` lesen-mutieren-schreiben ueber einen bounded Retry-Loop auf diesem Port, statt eine der beiden Aenderungen bei parallelen Aufrufen kommentarlos zu verlieren (Lost-Update-Schutz, `RequirementConcurrentlyModifiedException` bei Erschoepfung). `add()` umgibt zusaetzlich `nextCode()`+`create()` mit demselben Retry-Muster, um den TOCTOU-Race auf dem naechsten freien `FR-N`/`NFR-N` abzufangen -- bewusst **kein** serverseitiges Vergeben des naechsten Codes in der Adapter-Transaktion (haette die `create`-Port-Signatur und ~30 bestehende Tests angefasst): der Client-seitige Retry ist ein akzeptierter Scope-Cut fuer den Single-User-MCP-Kontext (ADR-001), keine vollstaendige Loesung. Lesen ist Code-first (`findByCode`). Die uc-BC (`ActorRef`/`RequirementRef`) folgt seit #89 derselben Bauart wie `TermRef` -- beide tragen eine `ResourceId`, keine ist mehr code-basiert. Damit `req_get`/`req_list` trotzdem `TERM-N` statt einer nackten IRI zeigen, haengt `arknet-requirements-adapter-mcp` (nicht der Core, nicht der Out-Adapter) zusaetzlich am In-Port `ResolveTerms` der ul-BC (siehe dort) -- rein lesend, fuer die Anzeige (ADR-008). `update` erfasst vor dem replace-by-identity **in derselben Tx** die `usesTerm`-Kanten, die der Lese-Join nicht binden kann, und haengt sie danach wieder an; diese bewahrten Kanten laufen bewusst **am Write-Gate vorbei** (Bestand bewahren, nichts Neues einfuehren; ADR-007-Nachtrag). Der einzige verbliebene nicht-bewahrbare Fall: Ziele, die keine IRI sind (Blank Nodes; `arkreq:usesTerm` hat kein `sh:nodeKind`, `ResourceId` kann keine Blank Nodes) -- erreichbar nur store-first (ADR-005), nicht ueber die Tools. Der Hexagon traegt zusaetzlich den In-Port `ResolveRequirements` (Bauart 1:1 zu ul `ResolveTerms`, #88): Batch-Aufloesung `getById(WorkspaceId, ResourceId...)` -> `List<ResolveRequirements.ResolvedRequirement>` (schlanker Record `ResolvedRequirement(ResourceId id, RequirementCode code)`, wirft nie) plus der dazugehoerige Out-Port `RequirementRepository#findByIds` (`VALUES`-gebundener SPARQL-Batch, Join nur ueber `dcterms:identifier`, bewusst ohne Typ-Filter, da FR und NFR beide gueltige Subjekte sind). Konsument seit #89: die uc-BC (`arknet-use-cases-adapter-mcp`) nutzt ihn analog zu `req -> ul`, um `RequirementRef` als `FR-N` statt IRI anzuzeigen. Ein Requirement traegt zusaetzlich `arkreq:acceptanceCriterion` (testbares Done-when, `List<String>`, Pflicht: SHACL `sh:minCount 1` als `sh:Violation`, kein Best-Practice-`sh:Warning` wie bei `priority`/`motivatedBy` -- Testbarkeit ist ein ISO-29148-Qualitaetsattribut, das arknet fuer Requirements beansprucht) -- `req_add` verlangt mindestens ein Kriterium, der Out-Adapter schreibt/liest die Literale wie `usesTerm` als eigene Praedikat-Tripel (ohne dessen Cross-BC-Komplexitaet, da reine Literale keine Identitaetsaufloesung brauchen) und bewahrt sie ueber `setStatus`/`linkTerm`s replace-by-identity-Schreibpfad. Weil `Requirement`s Konstruktor eine leere Liste bereits zurueckweist, kann kein Domain-Objekt den store-first erreichbaren Fall (Requirement ohne Kriterium) abbilden -- dessen SHACL-Ablehnung ist daher nur ueber einen direkt gebauten Kandidat-Graphen testbar, nicht ueber die `Requirement`-Fixtures. Der Lesepfad (`findByCode`/`findAll`) trifft denselben leeren Fall aber real: SHACL gated nur Writes, sodass ein Requirement ohne `acceptanceCriterion`-Tripel (Altbestand oder store-first angelegt) sonst die Konstruktor-Invariante verletzen und `req_get`/`req_list` zum Absturz bringen wuerde. Der Out-Adapter faengt das ab, indem er eine leere Kriterien-Liste beim Lesen durch einen fest verdrahteten Platzhalter (`LEGACY_ACCEPTANCE_CRITERION_PLACEHOLDER`) ersetzt, bevor sie den Konstruktor erreicht -- die Domain-Invariante bleibt unangetastet streng, der Altbestand wird sichtbar statt zu crashen. Derselbe Konstruktor weist zusaetzlich Duplikate und Blank-Eintraege zurueck; `readAcceptanceCriteria`/`readAcceptanceCriteriaBySubject` lesen jedes Literal nur ueber seine lexikalische Form (Sprachtag/Datentyp gehen verloren), sodass zwei store-first-Literale mit gleicher Form aber unterschiedlichem Sprachtag oder ein Whitespace-only-Literal eine **nicht-leere**, aber Konstruktor-illegale Liste ergeben koennen -- derselbe Platzhalter-Mechanismus filtert das seit #103 vorgelagert (`sanitizeAcceptanceCriteria`: Blanks raus, Dedupe nach lexikalischer Form), bevor er auf den All-Empty-Fall prueft. `findAll` gruppiert seine SPARQL-Zeilen ebenfalls nach Subject (dasselbe `LinkedHashMap`-Muster wie `findByIds`): `priority`/`qualityCategory` sind `OPTIONAL`-Felder ohne durchsetzbaren `sh:maxCount` und koennen store-first mehrere Werte tragen -- ohne Gruppierung erschiene dasselbe Requirement mehrfach im Ergebnis; der Adapter waehlt deterministisch den zuerst gesehenen Wert und loggt eine Warnung, wenn mehrere unterschiedliche Werte kollabiert wurden. `findByCode`s Typ-Join ist auf die beiden bekannten Requirement-Typen gefiltert statt jedes `rdf:type`-Tripel ungefiltert zu binden. Der Hexagon traegt zusaetzlich den read-only Tool `req_schema`: es beschreibt das `arkreq:`-Requirement-Vokabular (RequirementType, RequirementStatus, Priority) als Daten, damit ein MCP-Client die zulaessigen Werte nicht raten muss. Definition je Term stammt aus dem klassen-level `rdfs:comment`@de der Ontologie (`arknet-requirements.ttl`), die `values`-Liste bewusst aus den Java-Domain-Enums statt aus `requirements-shapes.ttl`s `sh:in`-Aufzaehlung -- `RequirementStatus` implementiert absichtlich nur eine MVP-Teilmenge der sechs Ontologie-Individuen (`PROPOSED`/`ACCEPTED`), und `req_schema` darf einem Client nie Werte melden, die `req_add`/`req_set_status` tatsaechlich zurueckweisen wuerden. Getragen vom Out-Port `RequirementSchemaSource`, dessen einzige Implementierung `KognioRdfRequirementRepositoryFactory#buildSchemaSource()` das Turtle einmalig parst und ein bereits fertig gebautes, RDF4J-freies Ergebnis zurueckgibt -- die Ontologie wird gelesen, nicht der Workspace-Store, daher kein `DatasetLifecycle` noetig.
- **arknet-ubiquitous-language**: zweite hexagonale BC (Bauart 1:1 zu requirements) -- arknet-ubiquitous-language-core + arknet-ubiquitous-language-adapter-kogniordf (Out) + arknet-ubiquitous-language-adapter-mcp (In). Glossar-Begriffe als SKOS-Concepts (`term_add`/`term_list`/`term_get`); `arknet:ubiquitousLanguageTerm` ist ein `skos:Concept`. Ein Term kann optional eine Actor-Facette tragen (derselbe Concept zusaetzlich `arkproc:HumanActor`/`SystemActor` + `actorRole`; `term_add` mit optionalem `actorKind`/`actorRole`) -- Pre-Req der Use-Case-BC. Opake Identitaet: `TermId` wrapt eine vom Kernel gemintete `ResourceId` (Subject-IRI, unveraenderlich), `TermCode` traegt die `TERM-N`-Semantik als reines Business-Label (`dcterms:identifier`) -- der MCP-Nutzer tippt den Code, nie die IRI. `save` zerfaellt in `create` (Identitaet neu, sonst `ResourceAlreadyExistsException`; Code-Kollision -> `DuplicateTermCodeException`) und `update` (Identitaet muss existieren, sonst `TermNotFoundException`), Existenz-Check per `ASK` **innerhalb** der Schreibtransaktion (kein TOCTOU), replace-by-identity bleibt; die Actor-Facette haengt am opaken Subject und zieht mit. Cross-BC: req->term loest per `dcterms:identifier`, uc->actor per `skos:prefLabel` (beide schemaunabhaengig). Der Hexagon traegt zusaetzlich den In-Port `ResolveTerms` (Batch-Aufloesung `getById(WorkspaceId, ResourceId...)` -> `List<ResolveTerms.ResolvedTerm>`; wirft nie -- eine nicht aufloesbare Id fehlt einfach im Ergebnis, der Aufrufer entscheidet ueber den Fallback) plus den dazugehoerigen Out-Port `TermRepository#findByIds` (ein `VALUES`-gebundener SPARQL-Batch, kein N+1). `ResolvedTerm(ResourceId id, TermCode code)` ist ein bei `ResolveTerms` genesteter schlanker Record -- der einzige Konsument (der req-In-Adapter) braucht nur Identitaet+Code, nicht `prefLabel`/`definition`/Actor-Facette; `findByIds` joint dementsprechend nur `identifier`. `findByIds` gruppiert seine Zeilen bewusst nach Subject statt sie 1:1 in `ResolvedTerm`s zu uebersetzen: `dcterms:identifier` traegt in `ulshapes` kein `sh:maxCount`, ein store-first Term mit mehreren Identifier-Tripeln liefert also mehrere Zeilen fuer dieselbe Identitaet, und ohne Gruppierung waere das genau der Vertragsbruch, den `ResolveTerms` ("die Terme", nicht "eine Zeile pro Praedikat-Kombination") ausschliessen soll. Ein store-first Term ohne `prefLabel`/`definition` (fuer `findByCode`/`findAll` Pflicht) ist ueber `findByIds` trotzdem aufloesbar, weil diese Felder dort nicht gejoint werden. Zweck: der req-MCP-Adapter rendert `req_get`/`req_list`s verlinkte Terme als `TERM-N` statt als IRI, ohne dass die requirements-BC (Core oder Out-Adapter) von der ul-BC abhaengt -- die Abhaengigkeit sitzt ausschliesslich im req-In-Adapter (Tor zu seinem eigenen Hexagon, nicht Teil von dessen Core). `findByCode`/`findAll` in `KognioRdfTermRepository` joinen `skos:prefLabel` mehrwertig (ein Concept kann mehrere sprachgetaggte Labels tragen), gruppieren die Zeilen pro Subject und waehlen ueber die injizierte `DisplayLocale` das anzuzeigende Label -- ein Concept wird nie wegen fehlender angeforderter Sprache verschluckt, sondern degradiert entlang der Fallback-Kette; `findByIds` (der `ResolveTerms`-Batch) bleibt davon unberuehrt, da er nur `identifier` joint. `skos:definition` traegt ebenfalls kein `sh:maxCount` und wird deshalb wie `prefLabel` als Kandidatenliste pro Subject gesammelt -- anders als bei `prefLabel` gibt es dafuer keine Sprachauswahl-Garantie, daher waehlt der Adapter deterministisch den zuerst gesehenen Wert und loggt eine Warnung, wenn mehrere unterschiedliche Werte kollabiert wurden.
- **arknet-use-cases**: dritte hexagonale BC (Bauart 1:1 zu requirements) -- arknet-use-cases-core + arknet-use-cases-adapter-kogniordf (Out) + arknet-use-cases-adapter-mcp (In). Flow-orientierte Cockburn-Use-Cases als `arkreq:UseCase` mit strukturiertem Step-Flow (`uc_add`/`uc_list`/`uc_get`); coarse-grained write (ein `uc_add`-Call) / fine-grained read. Opake Identitaet: `UseCaseId` wrapt eine vom Kernel gemintete `ResourceId` (Subject-IRI, unveraenderlich), `UseCaseCode` traegt die `UCn`-Semantik als reines Business-Label (`dcterms:identifier`) -- der MCP-Nutzer tippt den Code (`uc_get UC1`), nie die IRI. `save` zerfaellt in `create` (Identitaet darf noch nicht existieren -> `ResourceAlreadyExistsException`; Code-Eindeutigkeit -> `DuplicateUseCaseCodeException`) und `update` (Identitaet muss existieren -> `UseCaseNotFoundException`); der Out-Adapter prueft beides per `ASK` **innerhalb** der Schreibtransaktion (kein TOCTOU), replace-by-identity bleibt. **Steps sind opake Value Objects**: eigene, opak gemintete IRIs statt `/step/N`-Slug (kein schema-on-subjects; Ordnung lebt in `arkreq:position`), nur ueber das UseCase-Aggregat (`mainStep`/`extensionStep`) erreichbar, kein eigener Lese-Einstieg. Weil der Step-Node ein aggregat-internes VO ohne stabile Identitaet ist (unter replace-by-identity bei jedem Schreiben neu gemintet), wird er im **Out-Adapter** gemintet (Serialisierung), waehrend der UseCase-Root store-neutral im Service gemintet wird; delete folgt den Step-Kanten statt einem IRI-Praefix. `ActorRef`/`RequirementRef` tragen seit #89 die opake `ResourceId` des referenzierten Nachbarn (Bauart wie req `TermRef`), keinen Business-Code mehr: Aufloesung Actor-Name/FR-Code -> `ResourceId` sitzt hinter zwei Out-Ports (`ActorLookup` per `skos:prefLabel` + Human/System-Facetten-Constraint, `RequirementLookup` per `dcterms:identifier`), einmalig aufgerufen von `UseCaseService#add` statt bei jedem Lesen -- didaktische Ablehnung bei Unbekanntem/Mehrdeutigem bleibt ueber `UnresolvedReferenceException`. Der Lesepfad (`readBySubject`/`readSupportingActors`/`readMainStepRealises`) joint dadurch nicht mehr zwingend in die Nachbar-Graphen; ein fehlendes/umbenanntes `primaryActor.prefLabel` liess vorher den **ganzen UseCase** aus `findAll`/`findByCode` verschwinden, jetzt nur noch bei einem Blank-Node-Ziel (guarded, `FILTER(isIRI(...))`). `uc_add`/`uc_get` bleiben an der MCP-Grenze bei Namen/FR-Codes; die Anzeige-Rueckrichtung nutzt `ResolveTerms` (ul) + `ResolveRequirements` (req) mit IRI-Fallback, analog zu `RequirementMcpTools` -- macht `arknet-use-cases-adapter-mcp` zur zweiten Cross-BC-Maven-Dependency (ADR-008, nach req->ul), diesmal mit zwei fremden In-Ports.

## Konventionen

- Java-Package: `de.hauschel.arknet.*`
- GroupId: `de.hauschel.arknet`
- Modulverzeichnis == artifactId (ausnahmslos), und **jedes** Modul traegt das
  `arknet-`-Prefix -- auch BC-Submodule (`arknet-mcp`, `arknet-requirements`,
  `arknet-requirements-core`, `arknet-ubiquitous-language-adapter-mcp`).
  Keine Abkuerzungen im Modulnamen: der BC-Name wird ausgeschrieben
  (`arknet-ubiquitous-language-core`, nicht `ul-core`). Java-Packages duerfen
  weiterhin kuerzen (`de.hauschel.arknet.ul.*`) -- die Regel gilt fuer Modul-
  und Artefaktnamen, nicht fuer Packages.
- Turtle als Primaerformat (nicht JSON-LD)
- SHACL-Validierung bei jedem Load (RDF4J SHACL Sail)
- Projektionen als Plugin: `.sparql` + Template-Datei-Paar

## Skills (Claude Code Plugin)

- `skills/adr/` (ADR-Pflege) und `skills/req-interview/` (Requirements/Use-Cases/Glossar-Interview,
  zwei Einstiege Greenfield+Bestandscode).
- Geshippter Plugin-Inhalt (Skill-Text, `plugin.json`-Description, Forgejo-Repo-Description) ist
  **Englisch** -- arknet ist oeffentlich im Hauschel Plugin Marketplace gelistet, Zielgruppe
  englischsprachig. Was **in den Store** geschrieben wird (Requirement-/Use-Case-/Term-Text) bleibt
  **Deutsch** -- arknets eigene Ubiquitous Language, unberuehrt von dieser Regel.
- Geshippte Artefakte referenzieren keine externen Quellprojekte (Herkunft/Inspiration gehoert in
  PR-Beschreibung/Memory, nicht in den ausgelieferten Text -- er muss fuer sich stehen).
- `skills/adr/` ist noch Deutsch (Altfall von vor dieser Entscheidung, 2026-07-17) -- kein
  Nachziehen ohne explizite Entscheidung.
