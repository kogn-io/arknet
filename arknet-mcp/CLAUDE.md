# arknet-mcp

MCP-Server (Streamable HTTP, Spring AI 2.0 `spring-ai-starter-mcp-server-webmvc`) + Composition Root -- Spring Boot, verdrahtet requirements-Hexagon + ubiquitous-language-Hexagon + use-cases-Hexagon + bounded-context-Hexagon + adr-Hexagon + actor-Hexagon + project-Hexagon + model-analysis-Hexagon als `@McpTool`-Beans.
Eigene Anwendungslogik traegt dieses Modul nicht (ADR-55): geblieben sind die Verdrahtung, der typunabhaengige Lesepfad (`store_overview`, `resource_get`, `resource_history`, `project_export`), das Suchwerkzeug `text_search` und der HTML-Report, dessen Ort die Modellanalyse ist und der dort noch nicht liegt (#560).
Das project-Hexagon faellt dabei aus dem Muster der uebrigen sechs: es verwaltet Identitaet statt Modell, seine Registry wohnt im reservierten System-Dataset (`ProjectId.RESERVED_SYSTEM_DATASET`) statt in einem Projekt-Dataset, und seine `@McpTool`-Beans bekommen darum weder eine `ProjectId` noch den `ProjectResolver` -- sie lesen den Anker des Aufrufs roh und schlagen ihn selbst nach.
Das ist keine Auslassung, sondern zwingend: dieser BC beantwortet die Routing-Frage fuer alle anderen und kann darum nicht selbst hinter einer Antwort darauf liegen.
Die BC-Hexagons teilen den `ProjectResolver`-Bean UND einen gemeinsamen `DatasetLifecycle`-Bean -- ein Dataset pro Projekt, aber die ProjectId wird pro Tool-Aufruf aufgeloest (nicht als Singleton injiziert), damit ein Prozess alle Projekte bedienen kann.
Dieser `DatasetLifecycle`-Bean ist mit `mcp/dataset/LockConflictReportingDatasetLifecycle` dekoriert: ein injiziertes `Predicate<RuntimeException>` (Default `KognioRdfRequirementRepositoryFactory.DEFAULT_LOCK_CONFLICT`, der einzige Ort ausserhalb der Adapter-Factories, der RDF4Js `RepositoryLockedException` kennt) entscheidet, ob ein fehlgeschlagenes `acquire` tatsaechlich ein Sperrkonflikt eines zweiten Prozesses auf demselben Storage-Verzeichnis ist; nur dann uebersetzt der Dekorator die Store-Exception in eine erklaerende `DatasetLockConflictException`.
Jeder andere `acquire`-Fehler -- Rechteproblem, voller Speicher, defekter Store -- laeuft unveraendert durch, damit er nicht faelschlich als Lock-Konflikt gemeldet wird.
`arknet-mcp` bleibt dadurch frei von direkten RDF4J-Imports.
Ergaenzend haelt `mcp/dataset/DaemonStorageLock` eine eigene, exklusive Dateisperre ueber dem gesamten Storage-Root, aufgenommen noch vor dem `datasetLifecycle`-Bean (per `@DependsOn` in der Bean-Reihenfolge davor erzwungen): ein zweiter Daemon-Prozess ueber demselben Storage-Root scheitert damit schon beim Start und beruehrt nie ein Projekt-Dataset, statt mit dem ersten Daemon um ein eben erst angelegtes Dataset zu wettlaufen -- die Sperre pro Dataset allein schliesst dieses Zeitfenster nicht, weil beide Prozesse dieselbe Neu-Anlage-Pruefung noch vor ihrer jeweiligen Dataset-Sperre auswerten.
`LockConflictReportingDatasetLifecycle` ist zugleich `AutoCloseable` (`destroyMethod = "close"` auf dem `datasetLifecycle`-Bean): beim Herunterfahren schliesst es jedes von `list()` gemeldete Dataset ueber den neutralen Port, statt das geordnete Schliessen dem Crash-Recovery des Stores zu ueberlassen.
Das ist best-effort, kein garantiertes Schliessen: haelt ein paralleler `acquire`-Aufruf zum Shutdown-Zeitpunkt noch eine offene Lease auf einem Dataset, bleibt es offen -- statt darauf zu warten oder den Shutdown zu blockieren, loggt der Dekorator dafuer nur eine Warnung, und genau dieses Dataset faellt auf Crash-Recovery zurueck.
Beherbergt zusaetzlich den generischen, BC-uebergreifenden Store-Lesepfad (`store_overview`/`resource_get`/`resource_history`, readOnly; `resource_history` issue #251) -- Logik in `mcp/store/`, kein eigener BC.
Der Rueckgabewert von `store_overview` (Agent-Digest) kommt aus genau diesem generischen `SELECT ?s ?p ?o`; der HTML-Report daneben nicht mehr: `mcp/report/` setzt ihn pro Bounded Context aus deren Lese-In-Ports zusammen (`ListBoundedContexts`/`ListRequirements`/`ListUseCases`/`ListTerms`/`ListActors` plus `ResolveRequirements` fuer die Anzeige-Codes opaker Requirement-Referenzen -- geborgt als Borrowed In-Port; die Composition Root darf das, sie zieht ohnehin jedes Hexagon), weil ein aus Tripeln rekonstruierter Use Case kein lesbarer Use Case ist (Ablauf = `n` opake `arkreq:Step`-Subjekte, geordnet ueber ein `arkreq:position`-Literal).
Dieselbe Borrowed-In-Port-Rolle gilt fuer die Kopfzeile selbst: `StoreReportTools` fragt den neuen In-Port `FindProject` des Project-Hexagons je Aufruf ab und zeigt in Digest- und HTML-Kopfzeile das registrierte Label statt der rohen `ProjectId` -- mit Fallback auf die rohe id, wenn die Registry nichts liefert (jedes ueber `store_overview` erreichbare Projekt ist eigentlich bereits registriert, der Fallback ist also ein defensiver, kein regulaerer Pfad).
Ein Digest-Eintrag zeigt ein Label nur, wenn `StoreResource#label` es unter einem von vier generischen Praedikaten findet (`dcterms:title`, `skos:prefLabel`, `rdfs:label`, seit Issue #600 auch `arknet:name` -- das Praedikat, unter dem Actor/Role/BoundedContext/ADR ihren Namen tragen).
Eine Ressource ohne eines dieser vier Praedikate UND ohne `dcterms:identifier` -- ein `arkreq:Step`, ein `arkreq:AcceptanceCriterion`, jedes aggregat-interne Value Object ohne eigenen Lese-Einstieg -- erscheint seit Issue #600 nicht mehr als eigene Zeile, sondern zaehlt in eine Sammelzeile je `rdf:type`; die Regel ist rein strukturell (Label da? Identifier da?) und kennt keinen Typnamen.
Denselben Handle -- CURIE, sonst nicht-mehrdeutiger `dcterms:identifier`, sonst volle IRI -- zeigt seit Issue #594 auch `resource_get` fuer jede eingehende Referenz, nicht nur `store_overview` fuer jede gelistete Ressource: `mcp/store/ResourceHandles` haelt die Regel einmal, `DigestRenderer` und `StoreReportTools` (fuer `ResourceRenderer`s eingehende Nachbarn, dort mangels Store-Zugriff aus dem reinen Renderer herausgeloest) rufen sie beide auf.
Traegt das aufgeloeste `Project` zusaetzlich eine (mehrsprachige, bereits ueber die injizierte `DisplayLocale` aufgeloeste) Beschreibung, zeigt sowohl der Text-Digest (`DigestRenderer`, eine `# <description>`-Zeile direkt unter der Kopfzeile) als auch der HTML-Report (`HtmlReportRenderer`, `<p class="project-desc">` direkt unter `<header class="top">`) sie an -- fehlt sie, bleibt beides unveraendert wie vor dieser Beschreibung (issue #110).
Beide Renderer nehmen dafuer ein zusaetzliches `Optional<String> description`-Argument neben dem bereits vorhandenen `label`.
Fuer Glossar-Referenzen borgt der Report **nicht** `ResolveTerms`, sondern liest ueber `ListTerms` einmal je Report das ganze Glossar in die `Glossary`-Projektion: sie labelt jede Term-Referenz (der Chip zeigt das `skos:prefLabel`, der Code `TERM-n` wandert in den Tooltip) UND findet dieselben Labels im Prosatext der anderen BCs wieder.
Die schmale Identitaets-Aufloesung von `ResolveTerms` traegt kein Label und kennt nur die Terms, auf die schon eine Kante zeigt -- fuer die zweite Frage ("nennt dieser Text einen Begriff, auf den *keine* Kante zeigt?") braucht es alle.
Requirement-Beschreibung/Akzeptanzkriterien, BC-Domain-Vision und (seit Issue #333) jedes UseCase-Textfeld (`goal`/`scope`/`trigger`/`precondition`/`postcondition`, jeder Step-/Extension-Text) werden darum ausgezeichnet: eine Erwaehnung mit `arkreq:usesTerm`- bzw. `arkddd:ubiquitousLanguageTerm`-Kante wird zum Link, eine Erwaehnung ohne Kante zur sichtbaren Luecke (`Span.TermGap`) -- der Report behauptet damit keine Beziehung, die der Store nicht haelt, und macht die fehlende Kante auffindbar.
Der Abgleich ist absichtlich woertlich (case-insensitiv, Wortgrenze): deutsche Beugungen werden verfehlt, dafuer wird nie `Kundendienst` zur Erwaehnung von `Kunde`.
Die Chipliste unter dem Text schrumpft entsprechend auf die verlinkten Terms, die der Text *nicht* nennt.
Bei einem UseCase zaehlt zusaetzlich eine Erwaehnung seines eigenen `primaryRole`/`supportingRole` als Link, nicht als Luecke -- diese Beziehung ist bereits ueber die Rollen-Kante festgehalten, nur unter einem anderen Praedikat als `usesTerm` (Issue #333; vor Issue #333 blieb Use-Case-Prosa komplett unausgezeichnet).
Diese Deckung greift allerdings nur, wo die Rolle zugleich als Glossarbegriff gefuehrt wird: verglichen werden Term-IRIs, und seit dem Rollen-Schnitt (ADR-37) haben Rolle und Begriff getrennte Identitaeten, die sich nur bei Mehrfach-Typisierung derselben IRI ueberhaupt treffen.
`ModelViews` haelt die sieben Abschnitte und liest das Glossar als **eine** Quelle fuer alle (faellt dieser Lesevorgang aus, meldet er sich wie ein Abschnitt und der Rest steht weiter, nur ohne Labels und Auszeichnung).
Ein Render-neutrales Praesentationsmodell (`ModelCard`/`Block`/`Ref`/`RichText`+`Span`) trennt "welches Feld ist welche Form" (Karten-Builder) von "wie sieht eine Form aus" (`HtmlReportRenderer`) -- derselbe Schnitt, den ein zweiter Renderer wie eine spaetere Vaadin-Review-UI braucht; welche Erwaehnung Link und welche Luecke ist, entscheidet damit der Builder, nicht der Renderer.
Prosa-Felder tragen seit Issue #388 ein enges Markdown-Subset, das `ProseMarkdown` in der Kartenschicht liest -- neben `Glossary#markUp` und `CodeReferences`, nicht im Renderer.
Zugelassen sind `**fett**`, `*kursiv*`, `` `code` ``, `- `-Listen und Absaetze an Leerzeilen; ein einzelner Zeilenumbruch kollabiert wie in Markdown ueblich, ein unpaariger Marker bleibt Text, und `\*` schreibt ein literales Sternchen.
Nicht zugelassen sind Links, Ueberschriften, Tabellen, Bilder und eingebettetes HTML -- ein handgeschriebenes `[Actor](#term-3)` wuerde die modellvalidierte `usesTerm`-Kante und damit die `Span.TermGap`-Erkennung umgehen, also einen behaupteten Bezug an die Stelle eines geprueften setzen.
Ergebnis sind `ProsePart.Paragraph`/`ProsePart.Bullets` innerhalb **eines** `Block.Prose` (nicht mehrere Bloecke: ein Prosa-Feld ist ein Literal, und der Sprach-Switch wickelt genau ein Feld) sowie die Spans `Span.Emphasis`/`Span.Code`.
Ein Code-Run geht bewusst nicht durch das Glossar-Markup: `arkreq:usesTerm` in Backticks ist ein Bezeichner, kein Begriff.
Das Store-Literal bleibt roh -- geparst wird beim Lesen, `project_export` und der Agent-Digest (`DigestRenderer`) zeigen die Zeichen unveraendert.
Der Hinweis auf das Subset steht in der `@McpTool`-Beschreibung jedes schreibenden Tools (`PROSE_MARKUP` je BC-Adapter), weil der schreibende Agent das Tool-Schema liest und nicht diese Datei -- genau daran war der `pre-line`-Mechanismus aus #385 gescheitert.
Im HTML ist jede Karte eingeklappt (`details.fold`, Kopf = Code/Titel/Badges), die Toolbar hat Expand-/Collapse-all, und das Skript klappt Sprungziele wieder auf -- sonst liefe jeder Referenz-Link auf eine zugeklappte Karte.
Der Snapshot bleibt Auffangnetz: je Karte die Roh-Tripel eine Ebene tiefer, und alles, was kein BC als Modellelement beansprucht, in einem eigenen generischen Abschnitt -- der Report kann nichts verbergen, was im Store steht.
Neben den rohen Tripeln traegt jede Karte -- Modellkarte wie rohe Karte in "Other resources" gleichermassen -- einen `details.referenced-by`-Block (`HtmlReportRenderer#appendReferencedBy`): wer per eingehender Kante auf diese Ressource zeigt, mit Praedikat und Link auf die referenzierende Karte.
Die Grundlage ist ein einmal je Report aus `bySubject` gebauter Rueckwaerts-Index (`incomingByObject`), keine zweite SPARQL-Abfrage und kein Borrow -- derselbe Snapshot, den die rohen Tripel ohnehin schon zeigen, nur nach Objekt-IRI gruppiert.
Der Block ist bewusst ungefiltert (jede Kante zaehlt, unabhaengig vom Praedikat) und bewusst nicht `TraceabilityGraph#dependents`: der laeuft transitiv ueber eine feste Praedikat-Whitelist fuer `impact_analysis`, hier reicht ein einfacher Ein-Hop-Rueckwaertslookup, der dieselbe "nichts kann sich verstecken"-Haltung wie die rohen Tripel traegt statt Traceability-Relevanz vorauszusetzen.
Fuenf strukturelle Ausnahmen (issue #297 ergaenzt die zweite, issue #571 die dritte und vierte, issue #570 die fuenfte): von einem Use Case aus erreichbare `arkreq:Step`-Ressourcen, von einem Requirement aus erreichbare `arkreq:AcceptanceCriterion`-Ressourcen, von einem ADR aus erreichbare `arkarch:Consequence`- und `arkarch:ConsideredOption`-Ressourcen sowie eine `arkddd:ContextRelationship`, deren `arkddd:upstream`/`downstream`-Kante auf einen gecardeten Bounded Context zeigt, erscheinen dort nicht doppelt, ein von keinem Use Case referenzierter Step, ein von keinem Requirement referenziertes Akzeptanzkriterium, eine von keinem ADR referenzierte Consequence/ConsideredOption bzw. eine Beziehung, deren beide Bounded Contexts nicht gecardet sind, dagegen schon.
Die fuenfte Ausnahme laeuft rueckwaerts: eine `arkddd:ContextRelationship` zeigt selbst auf die beiden Bounded Contexts, die sie verbindet (eigene Ressource, kein Feld auf einer der beiden Seiten), also sucht `HtmlReportRenderer#inliningSources` -- anders als die vier Ausnahmen davor -- Quellen mit einer Kante auf eine gecardete Ressource statt Ziele einer Kante von einer gecardeten Ressource aus.
`BoundedContextCards` rendert jede Beziehung, die `BoundedContextDetail#relationships()` (issue #565) fuer den jeweiligen Kontext liefert, als Chip in einem eigenen `Context map`-Block (`Block.Refs`, dasselbe Muster wie `AdrCards`' "Affects contexts"), Richtung und Beziehungstyp bereits im Chip-Label ausgeschrieben (z.B. `upstream of BC-1 (Published language)`).
Kein Abschnitt darf den Aufruf fallen lassen: ein werfender In-Port wird als sichtbare Warnung gemeldet, seine Ressourcen fallen in den generischen Abschnitt zurueck -- `store_overview` ist das Werkzeug, zu dem gegriffen wird, wenn der Store fuer kaputt gehalten wird, und ein still fehlender Abschnitt liesse sich dabei als "Store ist leer" missverstehen statt als Fehler in genau einem Lese-In-Port.
Der HTML-Report traegt daneben einen fuenften Abschnitt: `AdrCards` ("Architecture Decisions") baut ihn aus `ListAdrs`, das beide Supersessions-Richtungen bereits aufgeloest liefert, und borgt `ResolveRequirements`/`ResolveBoundedContexts` als Borrowed In-Port, um `addressesRequirement`/`affectsContext` als Business-Codes zu zeigen -- genau wie `uc_get`/`adr_get` es bereits tun.
`usesTerm` (kogn-io/arknet#393) laeuft dagegen wie bei `RequirementCards` ueber das ohnehin einmal je Report geladene `Glossary`: Context/Decision sowie jede Consequence-/ConsideredOption-Aussage werden gegen die eigenen `usesTerm`-Kanten markiert (Link/Gap), eine verlinkte, im Text nie genannte Kante bleibt als `UnmentionedTerms`-Chip sichtbar -- kein eigener Borrow-Port dafuer noetig.
Consequences und Considered Options rendern seit Issue #382 beide als eigene `Block.Bullets`-Liste (`AdrCards#CONSEQUENCES_LABEL`/`CONSIDERED_OPTIONS_LABEL`) statt als eckig geklammerter Rohtext bzw. ein zusammengefuehrter `Block.Prose`-Block -- die Klassifikation (`consequenceType`/`optionOutcome`) wird zum `Badge` (`Badge.Kind.Known.CONSEQUENCE`/`OUTCOME`, ein outcome-loses Legacy-Option-Item zu einem neutralen `Unclassified`-Badge), eine Considered Option traegt ihren Namen als eigenes `BulletItem#caption`-Feld statt mit `" - "` ans Rationale geklebt.
`HtmlReportRenderer`s Sprach-Switch (issue #358 machte mehr als eine `Block.Bullets`-Liste je Karte moeglich) ist fuer beide neuen Listen mitgezogen: `LangSources#bullets` traegt eigene Eintraege unter `CONSEQUENCES_LABEL`/`CONSIDERED_OPTIONS_LABEL`, positioniert ueber `arknet:position` -- die #357-eigene Core-Namespace-Property, nicht das aeltere `arkreq:position` der Use-Case-/Requirement-Bullets. Nur `BulletItem#caption` bleibt unswitchbar: eine Considered Option traegt zwei unabhaengig mehrsprachige Felder (`arknet:name` fuer die Caption, `arkarch:optionRationale` fuer den Text), und `LangSources` loest bislang nur ein Textfeld pro Item auf.
Jeder Block traegt im HTML eine aus seinem eigenen Label abgeleitete Klasse (`block b-decision`, `b-context`, ...), damit das Stylesheet den einen Block hervorheben kann, um dessentwillen ein Record ueberhaupt existiert -- die Entscheidung --, ohne dass `HtmlReportRenderer#appendBlock` dafuer einen Sonderfall je Abschnitt bekommt.
Prosa wird dabei nach dem zugelassenen Markdown-Subset gegliedert (`ProseMarkdown`: Absaetze an Leerzeilen, `- `-Listen, `**fett**`/`*kursiv*`/`` `code` ``; Links, Ueberschriften, Tabellen und HTML bleiben Text) und in ein `.prose-body`-Element gewickelt -- so bleibt ein sprachumschaltbares Literal ein Element, unabhaengig davon, wieviel Struktur darin steckt. Prosa traegt keine eigene Lesebreite: die Zeilenlaenge folgt der Karte, die Seite selbst waechst mit dem Fenster (`.wrap` = `min(1600px, 95vw)`), damit ein grosser Bildschirm nicht zu zwei leeren Raendern fuehrt.
`CodeReferences` laeuft danach einmal ueber die fertigen Sektionen und macht jeden im Fliesstext genannten Business-Code, der eine Karte hat, zum Link auf sie (`Span.CodeRef`, Tooltip = Code + Titel der Zielkarte): ein Kartenbauer sieht immer nur seinen eigenen BC, der Code zeigt aber typischerweise in einen fremden -- darum dieselbe Begruendung, aus der `ModelViews` zusammensetzt, statt die Bauer einander aufrufen zu lassen.
Ein Code ohne Karte bleibt bewusst Klartext (keine `TermGap`-Entsprechung: ein Satz, der ein ADR nennt, ist Prosa und keine Kante, die der Store haette halten sollen), und eine Karte verlinkt nie auf sich selbst.
Seit Issue #336 kommt ein sechster Abschnitt dazu: `ActorCards` ("Actors") baut ihn aus `ListActors` (kein geborgter Port -- ein Actor traegt in diesem Schnitt keine Referenz auf einen Nachbar-BC), der Typ (`HUMAN`/`SYSTEM`/`LEGAL`/`GROUP`) wird zum Badge (wiederverwendet `Badge.Kind.Known.ACTOR`, vormals das Term-Facetten-Badge), die optionale Beschreibung zum Prosa-Block; `TermCards` zeigt seitdem kein Actor-Badge mehr, da ein Term seit #336 keine Actor-Facette mehr tragen kann.
Seit Issue #390 kommt ein siebter Abschnitt dazu: `ConstraintCards` ("Constraints") baut ihn aus dem Requirements-Hexagons eigenem `ListConstraints` (`constraintService` war bereits fuer `constraint_*` verdrahtet, keine neue Bean noetig) -- bis dahin faellt ein `constraint_add`/`constraint_update` gemaess dem seit Issue #388 an jedem schreibenden Tool haengenden Markdown-Subset-Hinweis in die generische Rohsicht und zeigt die Markdown-Zeichen unverarbeitet, statt sie einzuloesen. Der Typ (`TECHNICAL`/`BUSINESS`/`REGULATORY`) wird zum `Badge.Kind.Known.TYPE` (Wert `TCON`/`BCON`/`RCON`, das Code-Praefix), `statement` zu einem `ProseMarkdown`-Block wie jedes andere Prosafeld; `title` bleibt wie bei jeder anderen Karte reiner Kartentitel, nicht geparst. Ohne Glossar-Markup und ohne geborgten Port, mirrort `ActorCards`' Begruendung fuer dieselbe Auslassung: ein Constraint traegt kein eigenes `arkreq:usesTerm`.
Seit ADR-37/kogn-io/arknet#405 (Teil B) kommt ein achter Abschnitt dazu: `RoleCards` ("Roles") baut ihn aus `roleService` (bereits fuer `role_*` verdrahtet, implementiert `ListRoles`, keine neue Bean noetig), mit `displayLocale` als echtem Parameter (anders als `ActorCards`, wie bei `ConstraintCards`, weil `name`/`description` einer Role sprachgetaggt sind); die optionale Beschreibung wird ein Prosa-Block, die aufgeloeste `filledBy`-Besetzung (Code + Name je Actor, oder `(unfilled)`) ein zweiter Prosa-Block, kein Badge -- eine Rolle traegt keinen Typ wie ein Actor oder Constraint.
Die `oslc_rm:constrainedBy`-Kante traegt diese Karte selbst weiterhin nicht (siehe `UseCaseCards`), erscheint aber ueber den generischen Referenced-by-Block (`HtmlReportRenderer#appendReferencedBy`) als eingehende Kante auf der Constraint-Karte, die sie constrained.
`UseCaseCards` bekommt denselben `roleService`-Bean ein drittes Mal, als `ResolveRoles`-In-Port: `primaryRole`/`supportingRole` werden als Name (unter `displayLocale` aufgeloest) + `ROLE-N`-Code gerendert, nicht ueber die `Glossary`-Aufloesung -- eine Rolle ist kein Glossarbegriff, ueber `Glossary` bliebe nur eine nackte IRI als toter Chip.
Das adr-Hexagon ist das einzige mit **zwei** Tool-Bean-Klassen im Composition Root: `AdrMcpTools` (die acht verwaltenden Tools) und, seit kogn-io/arknet#387, `AdrCheckMcpTools` ueber einen eigenen `AdrCheckService`-Bean fuer `adr_check` -- die lesende, nicht-blockierende Konsistenzpruefung ueber den ganzen ADR-Korpus.
`AdrCheckService` bekommt denselben `AdrService`-Bean als `ListAdrs`- und `CountSkippedAdrs`-In-Port, den auch `AdrMcpTools` und `AdrCards` schon nutzen; ein zweiter Lesepfad entsteht nicht, und geborgt wird hier gar nichts -- die Pruefung liest keine Nachbar-Ressource, nur den Korpus und die Codes, die er in seiner eigenen Prosa nennt.

Der Pruefpfad `store_check` und die fuenf Auswertungen (`trace_matrix`, `orphan_check`, `impact_analysis`, `role_usecase_matrix`, `term_cooccurrence`) liegen nicht hier, sondern in der Komponente des Bounded Context Modellanalyse (`arknet-model-analysis`, BC-6, ADR-54); die Composition Root verdrahtet ihre Beans und stellt ihre Werkzeuge bereit, mehr nicht.
Wie sie lesen und was sie melden: `arknet-model-analysis/CLAUDE.md`.

Daneben das Suchwerkzeug `text_search` (readOnly, kogn-io/arknet#594 Teil 1) in `mcp/search/`, ebenfalls Composition-Root-In-Adapter ohne eigene Domaene: eine Pflicht-Query als Substring, gross-/kleinschreibungs-unabhaengig, ueber jedes Literal des Projekts und jeden Sprachtag hinweg -- die Volltextsuche, die `impact_analysis` (nur Kanten) nicht bietet.
Der Treffer selbst laeuft als eigener SPARQL-Lesepfad (`StoreReader#literalContaining`, `FILTER(CONTAINS(LCASE(STR(?o)), LCASE(?q)))`), nicht ueber `readSnapshot`: die Nutzereingabe wird ueber den gebundenen `?q`-Parameter von kognio-rdfs `SparqlQuery#select(String, Map)` eingesetzt, nie in den Query-Text verkettet.
Jeder Treffer nennt die Ressource, unter der er gemeldet wird, als Business-Code oder CURIE (`ResourceHandles#of`, seit Issue #594 public statt paketprivat, damit `mcp/search` sie ohne dritte Kopie wiederverwendet), das getroffene Feld als CURIE, den Sprachtag und ein rund 40-Zeichen-Snippet um die Fundstelle (Zeilenumbrueche zu Leerzeichen geglaettet).
Ein `arkreq:Step` bzw. `arkreq:AcceptanceCriterion` traegt keinen eigenen Business-Code: `SearchHitResolver` klettert dann rein strukturell ueber die erste eingehende Kante zum naechsten Subjekt mit `dcterms:identifier` hoch (`ADR-51`/`ADR-55` binden den generischen Lesepfad an Typunabhaengigkeit, also kein typspezifischer Code fuer "das ist ein Step") und nennt die dabei durchquerte Kante im Treffer.
Treffer werden je Ressource gruppiert, eine Kopfzeile nennt die Trefferzahl, ab 200 Treffern (`TextSearchMcpTools#MAX_HITS`) wird abgeschnitten und die Kopfzeile sagt es; eine leere Query wird mit einer Handlungsempfehlung abgelehnt statt eine Ergebnisliste ueber jedes Literal zu bauen.

Der generische Store-Lesepfad selbst (`StoreReader`, das typunabhaengige Lesemodell `Triple`/`RdfNode`/`StoreResource`/`StoreSnapshot`, `Prefixes`, `HandleResolver`, `ResourceRenderer`, `Revision`) liegt seit dem Model-Analysis-Schnitt in `arknet-persistence-support`: ihn lesen die verbliebenen typunabhaengigen Werkzeuge dieses Moduls und der Out-Adapter der Modellanalyse gleichermassen.
`StoreReader` klammert **zwei** Infrastruktur-Graphen aus **allen drei** Lesepfaden aus; `readSnapshot`, `outgoing` und `incoming` teilen sich dafuer einen einzigen Filter-Baustein (`excludingInfrastructure` ueber die Liste `HIDDEN_GRAPHS`), damit der Ausschluss nicht zwischen Snapshot und Nachbarliste auseinanderlaufen kann.
Ausgeblendet sind der Provenance-Graph (`ArkprovVocabulary.PROVENANCE_GRAPH`) und die Selbstbeschreibung des Projekts (`ArkprjVocabulary.IDENTITY_GRAPH` Punkt 7) -- Anker und Label, ueber die der Aufruf ueberhaupt hierher geroutet wurde.
Die Registry selbst braucht keinen Ausschluss: sie liegt in einem reservierten Dataset, das kein gewoehnlicher Aufruf adressiert, waehrend die Selbstbeschreibung per Konstruktion IM gelesenen Dataset liegt.
`store_overview`/`resource_get` zeigen weiterhin das Modell, nie seine Aenderungshistorie -- der Trail waechst mit jedem Write, und jede Revision zeigt via `prov:specializationOf` auf ihre Ressource.
Auch der `arkprov:head`-Zeiger bleibt dort aussen vor, obwohl genau einer je Ressource begrenzt und billig zu zeigen waere und obwohl er ein nutzbares Concurrency-Token ist -- alle vier vormals umgangenen Pfade (`req_update`/`req_set_status`/`req_link_term`/`term_update`) bewegen ihn jetzt, da sie durch `WriteFunnel#compareAndUpdate` laufen.
Die frueher offene Frage, ob und wie die Historie ueberhaupt sichtbar wird, ist mit issue #251 fuer den Trail selbst beantwortet, nicht durch einen im Modell-Lesepfad gerenderten Head: `resource_history` (`StoreReportTools`) ist ein eigenes, bewusst separates Tool, das `StoreReader#history` direkt gegen `ArkprovVocabulary#PROVENANCE_GRAPH` fragt -- die eine Ausnahme von `StoreReader`s Infrastruktur-Ausschluss, keine Aufweichung davon; `store_overview`/`resource_get` bleiben unveraendert blind fuer diesen Graphen.
Zurueckgegeben wird je Ressource die Liste ihrer `arkprov:Revision`s, aeltest zuerst, mit der Revision markiert, deren IRI dem aktuell gelesenen `arkprov:head` entspricht; eine Ressource, die nie durch den Trichter geschrieben wurde (store-first, oder aelter als der Trichter), hat eine leere, aber fehlerfreie Historie -- `resource_history` prueft Existenz separat ueber `outgoing`/`incoming`, genau wie `resource_get` es fuer sein eigenes "nicht gefunden" tut.
`Prefixes.defaults()` traegt seitdem genau eine Revisions-Bindung (`rev:` -> `ArkprovVocabulary#REVISION_IRI_BASE`, dafuer aus einer vormals `WriteFunnel`-privaten Konstante in die geteilte Vokabularklasse gehoben), aber weiterhin keine `arkprov:`/`prov:`-Praedikat-Bindungen -- `resource_history` rendert eine kuratierte Sicht (laufende Nummer, Zeitstempel, current-Markierung), keine rohen Tripel, und braucht sie darum nicht.
`TraceabilityMcpTools#readGraph` (heute in `arknet-model-analysis`) loest seit issue #274 nicht mehr die prozessweite, injizierte `DisplayLocale`-Bean unveraendert auf, sondern mischt je Aufruf die `defaultLanguage` des ueber den Anker aufgeloesten Projekts ein (`DisplayLocale#withRequestedOverride` ueber die Anker-Aufloesung seines eigenen Adapters) -- ohne das waehlte `LabelMentions`s Suchmuster fuer einen mehrsprachigen Term dieselbe Sprache wie der Daemon-Default statt die des Projekts, wodurch eine woertliche Erwaehnung in der jeweils anderen Sprache unentdeckt blieb (derselbe Mechanismus, den `term_get` schon seit `effectiveDisplayLocale` beherrscht).
`store_overview`/`resource_get` (`StoreReportTools`) ziehen seit issue #276 denselben Merge nach: `DigestRenderer`/`HtmlReportRenderer` backen die Locale nicht mehr in ihren Konstruktor, `StoreReportTools` loest sie stattdessen je Aufruf ueber `AnchorContext#resolveResolvedProject` auf und mischt sie per `withRequestedOverride` ein, `ModelViews#of` faedelt dieselbe gemergte Sprache zusaetzlich in `ListTerms#list` -- der Glossar-Abschnitt widerspricht `orphan_check`/`term_get` seither nicht mehr beim Label desselben Terms.
Dieselbe Luecke eine Ebene tiefer ist mit issue #281 geschlossen: `ListRequirements#list`/`ListUseCases#list` nehmen seither einen `displayLocale`-Parameter entgegen und wenden dieselbe Fallback-Kette an wie `req_get`/`uc_get` (issue #229) -- `RequirementCards`/`UseCaseCards` im HTML-Report ziehen den gemergten Wert ueber `ModelViews#of` nach, siehe issue #276 oben.

Betriebsmodell: EIN geteilter, langlebiger Daemon fuer alle Projekte der Maschine auf
`127.0.0.1:47331` (Loopback-only, daher ohne Authentifizierung) statt eines stdio-Subprozesses pro
Claude-Code-Session -- Grund: mehrere Sessions/Worktrees desselben Projekts teilen einen Store und
kollidierten als eigene Subprozesse am NativeStore-Verzeichnis-Lock. Die Loopback-Grenze ist
durchgesetzt, nicht nur behauptet: `AnchorHttpTransportConfiguration` setzt auf dem
`WebMvcStreamableServerTransportProvider`-Bean einen `DefaultServerTransportSecurityValidator`
mit einer Host-Allowlist aus `127.0.0.1:*`/`localhost:*` -- Spring AI MCPs Default waere
sonst `ServerTransportSecurityValidator.NOOP`, der den Origin-/Host-Check aufruft, aber nichts
prueft, und liesse einen per DNS-Rebinding same-origin gemachten Request durch.
Der Port bleibt in der Allowlist bewusst als Wildcard offen statt auf den `application.properties`-
Default `47331` gepinnt: `server.port` ist ueber `arknet.mcp.port` selbst konfigurierbar, und eine
auf den Default gepinnte Allowlist haette jeden Aufruf gegen einen ueberschriebenen Port mit einem
421 abgelehnt, das weder Ursache noch Abhilfe nennt (issue #295) -- die DNS-Rebinding-Abwehr haengt
am Hostnamen, nicht am Port, der Wildcard ist also sicherheitsaequivalent.

Welches Projekt ein Aufruf trifft, entscheidet der **Anker**: eine opake Zeichenkette, die der
Client mitschickt und die der Server ausschliesslich nachschlaegt. Sie kommt pro Aufruf
aus dem `.mcp.json`-Header `X-Arknet-Project-Anchor: ${PWD}` --
`AnchorHttpTransportConfiguration` ueberschreibt den Spring-AI-Transport-Provider mit einem
`contextExtractor`, der den Header unter `ProjectResolver.ANCHOR_KEY` in den
`McpTransportContext` legt; die `*McpTools` lesen ihn dort pro Call und loesen ihn ueber den
`ProjectResolver`-Bean (`RegisteredAnchorProjectResolver` -> `ResolveProject` des
`arknet-project`-BC) auf. Alternativ nimmt **jedes projekt-adressierende** Tool einen optionalen
`projectAnchor`-Parameter, damit ein Client ohne Header-Kontrolle nicht ausgesperrt ist; der Header
bleibt Primaerweg, weil ein per Parameter uebergebener Anker vom Sprachmodell
stammt und ein geratener, aber zufaellig existierender still das falsche Projekt traefe.
`project_export` ist der Sonderfall dazu: es adressiert nur mit `projectOnly=true` ein einzelnes Projekt und nimmt den Parameter deshalb zwar an, lehnt ihn ausserhalb dieses Scopes aber ab, statt ihn stillschweigend fallenzulassen.
Fuer jedes Modell-adressierende Tool gilt: fehlender oder unbekannter Anker ist ein Fehler mit
nach Aufrufstelle getrennter Meldung -- **kein** Default, **kein** Rueckfall auf das
Daemon-Arbeitsverzeichnis. Die benannte Ausnahme sind die beiden Tools des
`arknet-project`-BC, die auf der Registry selbst arbeiten statt ein Projekt zu adressieren:
`project_list` (listet ausnahmslos alle registrierten Projekte) und `project_export` in seinem
Default-Scope ohne `projectOnly=true` (exportiert ausnahmslos alle registrierten Projekte).
Beide nehmen deshalb ueberhaupt keinen Anker entgegen -- ein Backup oder eine Projektuebersicht
ist naturgemaess projektuebergreifend, und die Registry kann sich nicht hinter einer Anker-
Aufloesung verstecken, die sie selbst beantwortet (issue #149). Der Header ist
Projekt-Routing, keine Authentifizierung. Weil das Projekt pro Aufruf aus dem Anker kommt,
genuegt ein Port fuer alle Projekte. Ein HTTP-Eintrag in `.mcp.json` ist bei Claude Code rein passiv
(nur Verbindungsaufbau, kein Prozess-Spawn/-Management) -- Start und Betrieb des Daemons sind Sache
des Menschen, siehe `README.md`.

Der geteilte Daemon aktualisiert sich nach einem Merge oder Release nicht selbst.
Er laeuft auf dem Image weiter, das beim letzten Start geladen war.
Neu bauen und ersetzen im Repo-Root mit `docker compose up --build -d --force-recreate`; ohne
`--force-recreate` bleibt der alte Container trotz neuem Image stehen.
Welchen Stand der Daemon tatsaechlich faehrt, zeigt `serverInfo.version` aus der MCP-`initialize`-
Antwort (siehe `README.md`, Abschnitt "Which build is running?"; ein lokaler Compose-Build ohne
`ARKNET_VERSION`-Build-Arg meldet `dev`), ersatzweise die Tool-Zahl in
`docker logs <container> | grep "Registered tools"`.
Ein bereits geladenes Tool-Schema in einer laufenden Client-Session kann veraltet sein; ein echter
Tool-Aufruf zeigt das neue Serververhalten sofort, `ToolSearch` erst nach erneutem Abruf.

`RegisteredAnchorProjectResolver` ist bewusst **ohne Cache**: die Aufloesung ist ein lokaler
Store-Read auf ein Subjekt, das die Registry direkt indiziert -- billig genug, dass ein Cache wenig
brauechte und Korrektheit genau an der Kante koestete, die am meisten zaehlt. Ein eben angelegtes
oder adoptiertes Projekt muss beim naechsten Aufruf aufloesen, sonst schiene der Ausweg, den die
Fehlermeldung gerade genannt hat, nicht zu funktionieren. (Ein Staleness-Fenster lohnt sich nur
gegen Kosten in der Groessenordnung eines Prozess-Starts, nicht gegen einen indizierten Read.)

Der HTML-Report von `store_overview` landet **immer** im serverseitigen
`arknet.report.dir/<projectId>`, nie im Verzeichnis des Clients: der Header traegt einen Anker,
keinen Pfad, und ihn an `Path.of` zu reichen waere genau die Interpretation, die der Anker
ausschliesst -- fuer einen `url`/`uuid`-Anker ginge sie ohnehin schief. Im containerisierten
Betrieb ist es der einzige erreichbare Ort, weil das Verzeichnis des Clients im Container nicht
existiert. Der projekt-scoped Unterordner ist damit das einzige, was zwei Projekte im
gemeinsamen Report-Verzeichnis auseinanderhaelt.

Seit issue #391 traegt derselbe Report zusaetzlich einen zweiten, browserfaehigen Zugang: `StoreReportController` (`mcp/store/`) registriert `GET /report?projectAnchor=<anchor>` als gewoehnlichen `@RestController` neben dem MCP-Streamable-Endpunkt und liefert genau dasselbe HTML als Response-Body statt eines Dateipfads -- additiv, `store_overview` schreibt weiterhin unveraendert die Datei.
Der Anker kommt hier zwingend als Query-Parameter, nicht als Header: ein Browser, der eine URL aufruft, kann `X-Arknet-Project-Anchor` nicht setzen, darum loest `StoreReportTools#htmlReport` (package-privat, Gegenstueck zu `storeOverview` ohne Datei-Seiteneffekt) den Anker ausschliesslich ueber den expliziten Parameter auf, ohne den Transport-Context-Fallback.
Ein `@RestController`, der neben dem `WebMvcStreamableServerTransportProvider`-Bean haengt, erbt dessen `DefaultServerTransportSecurityValidator` nicht automatisch -- `StoreReportController` prueft Host/Origin darum selbst, gegen dieselbe Allowlist wie der MCP-Transport, gehoben in die geteilte `LoopbackHostSecurity` (statt einer zweiten, unabhaengig gepflegten Kopie der `127.0.0.1:*`/`localhost:*`-Liste), damit ein per DNS-Rebinding auf den Daemon umgeleiteter Origin nicht das ganze Architekturmodell lesbar macht.

Die kompakte Kartenansicht zeigte bis issue #270 (Teil 2 von #248) nur die zum Report-Zeitpunkt per `DisplayLocale` aufgeloeste Sprache eines mehrsprachigen Feldes, obwohl jede Sprachvariante schon in der Rohtripel-Ansicht der eigenen Karte lag.
`HtmlReportRenderer#languageVariants` schliesst diese Luecke rein client-seitig, ohne neue Domain-/Port-Plumbing: sie matcht den gerade angezeigten Text eines Kartentitels oder `Block.Prose`-Feldes per Text-Gleichheit gegen die Literale der Karten-eigenen `raw`-`StoreResource` zurueck auf ein Praedikat -- traegt `subject` mehr als ein Praedikat mit demselben Text, gilt der Rueckmatch als mehrdeutig und bleibt ohne Switch, statt am falschen Feld zu raten.
Ein ungetaggtes Literal (Altbestand vor issue #258, oder `DisplayLocale`s Fallback-Stufe 3) zaehlt als Kandidat unter `displayLocale.systemDefault()`.
Gefundene Varianten rendert `langSwitchable` als `.lang-variant`-Elemente in einer `.lang-group`-Huelle (nur die aktive Sprache sichtbar; `<span>` innerhalb eines Satzes, `<div>` um ein Prosa-Feld, das selbst aus Bloecken besteht) -- eine inaktive Variante wird dabei durch dasselbe Markdown-Subset gerendert wie die aktive, nur ohne Glossar-Markup, damit ein Sprachwechsel nicht ploetzlich rohe Sternchen zeigt, ein Toolbar-`<select>` plus IIFE-Script scannt die `data-lang`-Attribute des Dokuments und schaltet um, mit Fallback auf die Default-Sprache eines Feldes, falls die gewaehlte Sprache dort keine Variante hat.
Seit issue #319 gilt derselbe Switch auch fuer die positionierten Karten-Items: Flow-Schritte, Use-Case-Extensions und Requirement-Akzeptanzkriterien.
Die haengen an eigenen `arkreq:Step`-/`arkreq:AcceptanceCriterion`-Sub-Ressourcen statt an der Karten-eigenen `raw`-Tabelle -- `langSources` sammelt sie je Karte aus derselben Snapshot-Tabelle ueber die `mainStep`/`extensionStep`/`acceptanceCriterion`-Kanten, ohne zusaetzlichen Store-Zugriff.
Gepaart wird ueber `arkreq:position` gegen `FlowStep#position`/`BulletItem#position` statt ueber Text-Gleichheit: zwei woertlich gleiche Schritte sind realistisch und machten den Text-Rueckmatch mehrdeutig, die Position ist es nie.
Der Text kommt darum mit explizitem Praedikat (`arkreq:stepText` bzw. `arkreq:criterionText`).
Beansprucht mehr als eine Sub-Ressource dieselbe Position, bleibt das Item ohne Switch -- dieselbe "lieber gar nicht als falsch"-Regel wie beim mehrdeutigen Text-Rueckmatch.
Seit issue #358 fuehrt `langSources` je `Block.Bullets`-Liste eine eigene Positionstabelle, geschluesselt ueber das Block-eigene Label (geteilte Konstante zwischen Karten-Builder -- `RequirementCards#ACCEPTANCE_CRITERIA_LABEL`, `UseCaseCards#EXTENSIONS_LABEL` -- und Renderer) statt einer einzigen, ueber alle Bullet-Listen einer Karte geteilten Tabelle: eine Karte mit zwei Bullet-Listen (z.B. Extensions und Akzeptanzkriterien, sollte je eine Karte beides zeigen) wuerde sich sonst an Positionskollisionen selbst blockieren oder ein Item mit der falschen Sub-Ressource paaren. Der Renderer muss den Kartentyp weiterhin nicht kennen, und `Block` bleibt shape-generisch -- die Kanten-/Praedikat-Verdrahtung bleibt Wissen von `HtmlReportRenderer#langSources`, nicht von `Block`.

Welchen Stand der Daemon faehrt, sagt er selbst -- an drei Stellen aus **einer** Quelle (issue #194).
Die Quelle ist die Property `arknet.version` (`application.properties`): `ARKNET_VERSION` gewinnt (vom Docker-Build aus Release-Tag bzw. Commit-Sha eingebacken, issue #159), sonst `build.version` aus dem `build-info`-Goal des `spring-boot-maven-plugin` (das Maven-`${revision}` des laufenden Jars, ueber `spring.config.import=optional:classpath:META-INF/build-info.properties` als Property lesbar), sonst der Platzhalter `unknown` fuer einen Lauf ohne beides (IDE-Start gegen einen nie gepackten Quellbaum).
Die drei Stellen sind der MCP-`initialize`-Handshake (`spring.ai.mcp.server.version`, was jeder Client ohnehin sieht), der Metadaten-Graph jedes `project_export`-Dumps und das Suffix ` [arknet <version>]` an jeder fehlgeschlagenen Tool-Antwort.
Dass es eine Quelle ist und nicht drei, ist der Punkt: ein Daemon, der sich in der Fehlermeldung anders nennt als im Handshake, verschaerft genau die Verwechslung, die er aufloesen soll.
`mcp/version/ServerVersion` traegt Version plus Build-Zeit und degradiert auf `unknown` ohne Build-Zeit, wenn keine `build-info.properties` auf dem Classpath liegt -- ein erkennbarer Platzhalter statt einer plausiblen Falschangabe.
Das Suffix haengt `mcp/version/ToolErrorVersionStamp` an, ein `BeanPostProcessor` ueber der einen `List<SyncToolSpecification>`, die Spring AIs Annotation-Scanner aus allen `@McpTool`-Methoden baut: eine Stelle deckt alle sieben Hexagons ab, ohne Proxy (die `*McpTools`-Klassen sind `final`), ohne Aspekt-Framework und ohne dass ein neuer BC etwas dafuer tun muesste.
Die Liste wird ueber ihren Inhalt erkannt, nicht ueber den Bean-Namen -- ein umbenannter Spring-AI-Bean soll das Suffix nicht lautlos abschalten.
Angehaengt wird, nicht ersetzt: die Remedy-Meldungen aus #137 (`DatasetLockConflictException`, die Unknown-Anchor-Meldung von `RegisteredAnchorProjectResolver`) muessen den Stempel unbeschadet ueberleben, sonst kostet die Versionsangabe genau den Satz, der sagt, was zu tun ist.
`mcp/version/OntologyVersions` liest die `owl:versionInfo` der sieben ausgelieferten Ontologie-Module vom Classpath -- mit einem bewusst engen Zeilen-Scan, keinem Turtle-Parser: arknet-mcp darf RDF4J nicht nennen (ArchUnit-Regel 5) und die technologieneutralen kognio-rdf-Ports tragen einen Serialisierer, aber keinen Parser.
Genau diese Fragilitaet nagelt `OntologyVersionsMatchOntologyTest` in `arknet-architecture-tests` fest: dort wird gegen einen echten RDF4J-Parse derselben Dateien verglichen, sodass ein umformatierter Ontologie-Header rot wird statt die Envelope still zu leeren.
`mcp/store/ExportMetadata` rendert daraus den Graphen `https://w3id.org/arknet/model/export-metadata`, den `StoreExporter` als TriG-Text an jeden Dump anhaengt -- niemals in den Store geschrieben, nie durch das SHACL-Gate gelaufen, in einem eigenen benannten Graphen, damit ein Leser genau ihn wegwerfen kann und exakt das Dataset uebrig behaelt.
Inhalt: eine `prov:Activity` je Export (opake IRI unter `https://w3id.org/arknet/export/`, wie `WriteFunnel` seine Revisionen muenzt) mit `prov:endedAtTime`, `prov:wasAssociatedWith` auf den einen `prov:SoftwareAgent` `https://w3id.org/arknet/agent/arknet` (der `owl:versionInfo` und `dcterms:created` traegt) und `prov:used` auf jedes Ontologie-Modul mit dessen `owl:versionInfo`.
Eigene arknet-Terme braucht das nicht -- PROV-O, `owl:` und `dcterms:` decken es ab; die IRIs stehen als `ExportMetadataVocabulary` neben den uebrigen Vokabular-Klassen in `arknet-persistence-support`.
Fehlt die Build-Zeit, bleibt `dcterms:created` weg statt geraten zu werden.

**Der Sprachbestand je Feld (kogn-io/arknet#474).**
`StoreReader#languageTagsByField(DatasetId, String identifier)` liefert je Modell-Feldnamen (Local Name des Praedikats) die Sprachtags, die dieses Feld tatsaechlich traegt -- die Store-Seite des Hinweises, den jedes `*_update` bei einem einsprachigen Schreiben an seine Antwort haengt -- nachgeschlagen vor dem Write, weil nur der Zustand davor eine Korrektur von einer Uebersetzung unterscheidet (Mechanismus: `StaleTranslationHint` in `arknet-mcp-support`).
`StoreFieldLanguageLookup` implementiert damit den Port `FieldLanguageLookup` aus `arknet-mcp-support`; die Verdrahtung sitzt in `ArknetMcpConfiguration` und geht als **ein** Bean an alle sieben schreibenden In-Adapter -- dieselbe Richtung wie `RegisteredAnchorProjectResolver`: ein Port neben den Adaptern, eine Implementierung hier, ohne neue Modulkante.
Nur diese Klasse darf wissen, dass ein Projekt-Registry-Record in einem anderen Dataset liegt als eine Modell-Ressource -- daher nimmt die Lesemethode als einzige hier eine `DatasetId` statt einer `ProjectId` entgegen: das reservierte System-Dataset ist eine Id, die `ProjectId` per Konstruktion nicht halten darf.
Die Query ist **eine** mit zwei Hops: das Subjekt selbst und, ueber jede ausgehende Kante, dessen Objekt-Ressourcen -- so erreicht sie die besessenen Kind-Ressourcen (Akzeptanzkriterium, Schritt, Konsequenz), deren Text genauso mehrsprachig ist, gebuendelt unter dem Local Name der besitzenden Kante.
Sie unterscheidet dabei nicht zwischen besessenem Kind und benachbarter erstklassiger Ressource (ein verlinkter Term, ein adressiertes Requirement) -- das braeuchte Typwissen, das dieser Lesepfad nicht hat und nicht will; die zusaetzlichen Schluessel sind wirkungslos, weil ein Aufrufer nur nach den Feldern fragt, die er selbst geschrieben hat.
Anders als `readSnapshot`/`outgoing`/`incoming` laeuft sie **ohne** `excludingInfrastructure`, aus demselben Grund wie `findByIdentifier`: der Identifier-Treffer kann auch eine getombstonete Revision im Provenance-Graphen sein, die den Code einer geloeschten Ressource aufbewahrt -- eine Revision traegt aber kein sprachgetaggtes Literal, und was ihr `prov:specializationOf`-Hop beitraegt, landet unter diesem Praedikatnamen, nach dem kein Aufrufer fragt.

`spring.ai.mcp.server.instructions` in `application.properties` traegt seit kogn-io/arknet#522 zusaetzlich die ausfuehrliche Erklaerung der drei querschnittlichen Parameter `projectAnchor`/`language`/`displayLocale`, einmal fuer den ganzen Server statt wiederholt je Tool-Schema.
Jedes einzelne `@McpToolParam` dieser drei traegt dagegen nur noch die kurze Konstante aus `de.hauschel.arknet.mcpsupport.ToolParameterDescriptions` (arknet-mcp-support) -- der Grund, warum sie kurz sein darf, ist, dass die lange Fassung hier steht.
Vier Ausnahmen behalten eine eigene, laengere Beschreibung, wo der Parameter am jeweiligen Tool eine eigene Bedeutung traegt, die die geteilte Kurzfassung nicht mehr abdeckt.
`term_update`s `language` und `adr_check`s `displayLocale` erklaeren dort je eine eigene Sprachpartialitaets-Regel.
`project_add`s und `project_update`s `language` beschreiben stattdessen einen einfachen, ungetaggten Write ohne Projekt-Default-Rueckfall: ein Projekt hat keinen Default fuer sich selbst -- es *ist* die Quelle des Defaults der anderen BCs --, und so schreiben beide Tools bewusst ungetaggt, wo kein `language` mitkommt (Port-Kontrakt von `UpdateProject`).
Ein fuenfter Fall ist keine Ausnahme, sondern eine Verkettung: `project_export`s `projectAnchor` setzt die geteilte Konstante voran und haengt die tool-eigene Regel an, dass `projectOnly=true` den Anker zur Pflichtangabe macht.
